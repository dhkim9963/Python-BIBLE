\subsection{LEGB와 이름 탐색}

Name Resolution · Static Scope Analysis · UnboundLocalError · global

\subsubsection{이전 내용과의 연결}

\zsh{A.1}에서는 함수 객체의 생성, 이름 바인딩, 호출과 반환을 학습하였다.

\zsh{A.2}에서는 이를 중첩 함수(Nested Function)로 확장하면서 두 가지 사실을 확인하였다.

\begin{dhksmry}
    1. 함수 객체가 생성되는 시점과 함수 본문이 실행되는 시점은 다르다.

    2. 함수 내부의 이름 탐색은 호출 위치가 아니라
       
       정의 위치에 따른 렉시컬 스코프를 기준으로 한다.
\end{dhksmry}

그런데 여기서 해결하지 않은 문제가 하나 있다.

다음 코드를 보자.

\begin{dhkcode}
x = 10

def func():
    print(x)

func()
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
10
\end{dhkzsh}

\zsh{func()}의 지역 스코프에는 \zsh{x}가 없으므로 모듈의 전역 스코프에서 \zsh{x}를 찾은 것이다.

그렇다면 다음 코드는 어떨까?

\begin{dhkcode}
x = 10

def func():
    print(x)
    x = 20

func()
\end{dhkcode}

위에서 아래로 실행된다고 생각하면 \zsh{print(x)} 시점에는 아직 \zsh{x = 20}이 실행되지 않았으므로 전역 변수 \zsh{x = 10}을 사용할 것 같다.

하지만 실제로는 다음 예외가 발생한다.

\begin{dhkzsh}
UnboundLocalError: cannot access local variable 'x' 
where it is not associated with a value
\end{dhkzsh}

왜 이런 결과가 발생할까?

Python은 이름을 사용할 때마다 무조건 LEGB 순서로 모든 네임스페이스를 검색하는 것이 아니기 때문이다.

함수 본문을 실행하기 전에 해당 이름이 지역 이름인지, 외부 함수의 이름인지, 전역 이름인지 등을 판정하는 과정이 존재한다.

이번 학습에서는 이 원리를 정확하게 분석할 것이다.

\subsubsection{이번 학습의 핵심 질문}

이번 학습에서는 다음 질문에 답할 수 있어야 한다.

\begin{dhksmry}
    1. LEGB의 각 영역은 정확히 무엇을 의미하는가?

    2. 이름의 스코프는 언제 결정되고, 실제 객체는 언제 조회할까?

    3. 함수 안에 대입문이 있다는 이유만으로 
    
       왜 UnboundLocalError가 발생할까?

    4. global은 어떤 이름 바인딩 규칙을 변경할까?

    5. global과 nonlocal은 어떤 점에서 다를까?

    6. 이름 탐색(Name Resolution)과 객체의 속성 탐색(Attribute Lookup)은

       왜 구별해야 할까?
\end{dhksmry}

특히 다음 구분을 중심으로 설명할 것이다.

실행 시점에 그 이름이 참조하는 객체를 조회하는 과정은 다르다.
\end{dhksmry}

\subsubsection{LEGB의 정확한 의미}

LEGB는 Python에서 일반적인 이름 탐색을 설명하는 모델이다.

각 문자는 다음 영역을 의미한다.

\begin{dhktable}
|구분|명칭|의미|
|:---|:---|:---|
|L|Local|현재 함수 호출의 지역 스코프|
|E|Enclosing|렉시컬 구조상 현재 함수를 감싸는 외부 함수 스코프|
|G|Global|해당 함수가 속산 모듈의 전역 스코프|
|B|Builtins|Python의 내장 이름 스코프|
\end{dhktable}

기본적인 탐색 구조는 다음과 같다.

\begin{dhkgraph}[uniform]
node local (1,1) [accent] :: Local

group enclosing(local) :: Enclosing
group global(enclosing) :: Global
group builtins(global) :: Builtins

caption :: LEGB 네임스페이스의 포함 관계를 나타낸 개념도
\end{dhkgraph}

이 그림은 개념적인 스코프 구조를 나타낸다.

실제 CPython이 모든 이름에 대해 네 개의 딕셔너리를 순서대로 검색한다는 의미는 아니다.

일반적인 함수의 지역 변수는 최적화된 실행 환경에서 관리될 수 있고, 자유 변수는 셀(Cell)을 통해 접근할 수 있다.

또한 \zsh{global}과 \zsh{nonlocal} 선언은 이름의 분류 자체를 변경한다.

따라서 LEGB는 이름 탐색의 의미론적 구조를 이해하기 위한 모델로 사용하는 것이 정확하다.

\begin{dhknote}
\begin{dhksmry}[centered]
기본 예제
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x = "Global"

def outer():
    x = "Enclosing"

    def inner():
        x = "Local"
        print(x)

    inner()

outer()
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
Local
\end{dhkzsh}

\zsh{inner()}에서 사용한 \zsh{x}는 현재 함수의 지역 이름이므로 외부 스코프를 탐색할 필요가 없다.

이번에는 지역 바인딩을 제거해 보자.

\begin{dhkcode}
x = "Global"

def outer():
    x = "Enclosing"

    def inner():
        print(x)

    inner()

outer()
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
Enclosing
\end{dhkzsh}

\zsh{inner}에는 지역 이름 \zsh{x}가 없고, 렉시컬 외부 함수 \zsh{outer}의 \zsh{x}를 참조하므로 \zsh{"Enclosing"}이 출력된다.

다음으로 외부 함수의 \zsh{x}도 제거해 보자.

\begin{dhkcode}
x = "Global"

def outer():

    def inner():
        print(x)

    inner()

outer()
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
Global
\end{dhkzsh}

이제 \zsh{inner}의 \zsh{x}는 전역 이름으로 분류되고, 모듈의 \zsh{x}를 조회한다.

마지막으로 내장 이름을 살펴보자.

\begin{dhkcode}
def func():
    print(len([10, 20, 30]))

func()
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
3
\end{dhkzsh}

일반적인 실행 환경에서 \zsh{len}은 지역이나 전역 스코프에 별도로 정의되어 있지 않으므로 내장 이름을 사용한다.

여기까지는 익숙한 LEGB 설명이다.

하지만 이것으로는 \zsh{UnboundLocalError}를 설명할 수 없다.

\subsubsection{핵심 원리 - 이름의 정적 판정(Static Scope Analysis)}

Python은 함수 본문을 실행하기 전에 해당 함수 블록의 이름 사용과 바인딩을 분석한다.

이 과정에서 어떤 이름이 지역 이름인지, 자유 변수인지, 전역 이름인지 등이 결정된다.

이러한 분석은 함수 호출 시점에 처음 수행되는 것이 아니라, 일반적으로 소스 코드가 컴파일되는 과정에서 수행된다.

여기서 두 단계를 구분해야 한다.

\begin{dhknote}
\begin{dhksmry}[centered]
1단계. 이름의 분류
\end{dhksmry}
\end{dhknote}

컴파일 단계에서 함수 블록의 이름 사용을 분석한다.

예를 들어 다음과 같은 질문에 답하는 것이다.

\begin{dhksmry}
    - 현재 함수에서 x를 바인딩하는가?

    - x에 global 선언이 있는가?

    - x에 nonlocal 선언이 있는가?

    - x가 외부 함수의 바인딩을 참조하는가?
\end{dhksmry}

\begin{dhknote}
\begin{dhksmry}[centered]
2단계. 실행 시점의 객체 조회
\end{dhksmry}
\end{dhknote}

실제로 함수가 호출되면 해당 이름에 연결된 바인딩을 통해 객체를 조회한다.

따라서 다음 두 문장은 서로 다른 의미를 가진다.

이름의 스코프가 결정되었다.

그 이름에 객체가 바인딩되었다.

이름이 지역 변수로 분류되었다고 해서 그 지역 변수에 반드시 객체가 바인딩되어 있는 것은 아니다.

바로 이 차이가 \zsh{UnboundLocalError}의 원인이다.

\subsubsection{\zsh{UnboundLocalError}}는 왜 발생할까?

다음 코드를 다시 살펴보자.

\begin{dhkcode}
x = 10

def func():
    print(x)
    x = 20

func()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
UnboundLocalError: cannot access local variable 'x' 
where it is not associated with a value
\end{dhkzsh}

dㅖ외 메시지의 구체적인 표현은 Python의 버전에 따라 달라질 수 있다.

\begin{dhknote}
\begin{dhksmry}[centered]
1. 컴파일 단계
\end{dhksmry}
\end{dhknote}

Python은 \zsh{func}의 본문을 분석한다.

\begin{dhkcode}
def func():
    print(x)
    x = 20
\end{dhkcode}

여기서 다음 대입문을 발견한다.

\begin{dhkcode}
x = 20
\end{dhkcode}

일반적인 함수 블록에서 별도의 \zsh{global} 또는 \zsh{nonlocal} 선언 없이 이름에 대입하면, 그 이름은 해당 함수의 지역 이름으로 분류된다.

따라서 \zsh{func} 내부의 \zsh{x}는 지역 변수로 판정된다.

중요한 점은 대입문이 함수 본문의 뒤쪽에 있다는 사실이 이 판정에 영향을 주지 않는다는 것이다.

\begin{dhknote}
\begin{dhksmry}[centered]
2. 함수 호출
\end{dhksmry}
\end{dhknote}

이제 \zsh{func()}가 호출된다.

현재 호출의 지역 실행 환경에는 \zsh{x}라는 지역 이름을 위한 자리가 있지만, 아직 객체가 바인딩되지 않았다.

\begin{dhknote}
\begin{dhksmry}[centered]
3. print(x) 실행
\end{dhksmry}
\end{dhknote}

다음 문장이 실행된다.

\begin{dhkcode}
print(x)
\end{dhkcode}

Python은 이미 \zsh{x}를 지역 이름으로 판정했으므로 그 지역 바인딩에서 객체를 가져오려고 한다.

그런데 아직 \zsh{x = 20}이 실행되지 않았다.

따라서 \zsh{x}에는 객체가 바인딩되어 있지 않다.

그 결과 \zsh{UnboundLocalError}가 발생한다.

\begin{dhknote}
\begin{dhksmry}[centered]
4. 전역 변수로 넘어가지 않는 이유
\end{dhksmry}
\end{dhknote}

여기가 가장 중요하다.

전역 스코프에는 분명히 다음 바인딩이 존재한다.

\begin{dhkcode}
x = 10
\end{dhkcode}

하지만 \zsh{func} 내부의 \zsh{x}는 이미 지역 이름으로 판정되었다.

따라서 지역 이름을 읽는 과정에서 바인딩되지 않은 상태가 발견되었다고 해서 전역 스코프로 다시 탐색을 진행하지 않는다.

즉, 다음처럼 동작하는 것이 아니다.

\begin{dhksmry}[centered]
지역 x 발견
\da
아직 값이 없음
\da
전역 x 검색
\da
10 사용
\end{dhksmry}

실제 의미론적 동작은 다음에 가깝다.

\begin{dhkdiagram}[in=6]
node n1 (1,1) :: 컴파일 단계
node n2 (2,2) :: x를 지역 이름으로 판정
node n22 (3,2)
node n3 (3,1) :: 실행 단계
node n4 (4,2) :: 지역 x 읽기 시도
node n5 (5,2) :: 아직 바인딩 되지 않음
node n6 (6,2) :: UnboundLocalError

edge n1 -- n2 :: VH
edge n2 -> n22
edge n3 -- n4 :: VH
edge n4 -> n5
edge n5 -> n6
\end{dhkdiagram}

LEGB는 지역 이름이 바인딩되지 않았을 때 무조건 다음 스코프로 넘어간다는 규칙이 아니다.

이 차이를 정확하게 이해해야 한다.

\subsubsection{조건문 안의 대입도 지역 이름을 결정한다}

이제 조금 더 흥미로운 예제를 살펴보자.

\begin{dhkcode}
x = 10

def func():
    if False:
        x = 20

    print(x)

func()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
UnboundLocalError
\end{dhkzsh}

실제로 \zsh{if False} 내부의 대입문은 실행되지 않는다.

그런데도 \zsh{x}는 지역 이름으로 판정된다.

왜 그럴까?

함수 블록의 지역 이름 판정은 일반적으로 해당 대입문이 실제 실행되는지 여부와 독립적이기 때문이다.

컴파일러는 함수 블록에 있는 바인딩 연산을 분석한다.

따라서 다음 코드도 마찬가지다.

\begin{dhkcode}
x = 10

def func(flag):
    if flag:
        x = 20

    return x

print(func(True))
print(func(False))
\end{dhkcode}

첫 번째 호출에서는 20이 출력된다.

두 번째 호출에서는 \zsh{UnboundLocalError}가 발생한다.

여기서 중요한 차이는 다음과 같다.

\begin{dhktable}
|구분|func(True)|func(False)|
|:---|:---|:---|
|x의 스코프|Local|Local|
|x = 20 실행 여부|	실행|	실행되지 않음|
|지역 x 바인딩|	존재|	존재하지 않음|
|결과|	20|	UnboundLocalError|
\end{dhktable}

같은 함수의 이름 분류는 호출할 때마다 달라지지 않지만, 실제 바인딩 상태는 실행 경로에 따라 달라질 수 있다.

이것이 정적 스코프 판정과 동적 실행 상태의 차이다.

\subsubsection{대입 연산만 지역 이름을 만드는 것은 아니다}

지금까지는 \zsh{x = 20}을 중심으로 설명하였다.

하지만 지역 이름을 만드는 바인딩 연산은 대입문만 있는 것이 아니다.

예를 들어 함수 내부의 다음 구문도 이름을 바인딩할 수 있다.

\begin{dhkcode}
def func(x):
    ...
\end{dhkcode}

매개변수 \zsh{x}는 함수의 지역 이름이다.

\begin{dhkcode}
def func():
    import math
\end{dhkcode}

여기서 \zsh{math}도 지역 이름이다.

\begin{dhkcode}
def func():
    for item in [1,2,3]:
        pass
\end{dhkcode}

\zsh{item} 역시 지역 이름으로 분류된다.

또한 함수 내부의 \zsh{def, class, with ... as}, 

예외 처리의 \zsh{except ... as} 등도 바인딩에 관여할 수 있다.

다음 예제를 살펴보자.

\begin{dhkcode}
value = 100

def func():
    print(value)

    for value in []:
        pass

func()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
UnboundLocalError
\end{dhkzsh}

반복 대상이 빈 리스트이므로 \zsh{for}문의 본문은 실행되지 않는다.

하지만 \zsh{for value in ...}의 \zsh{value}는 함수 블록에서 바인딩 대상이 되는 이름이다.

따라서 \zsh{value}는 지역 이름으로 분류된다.

이름 분류는 단순히 \zsh{=} 문자의 존재만으로 결정되는 것이 아니라, Python 문법에서 어떤 구문이 이름을 바인딩하는지에 따라 결정된다는 점을 기억해야 한다.

\subsubsection{\zsh{global}의 정확한 역할}

이제 \zsh{global}을 살펴보자.

다음 코드를 실행해 보자.

\begin{dhkcode}
x = 10

def func():
    global x

    print(x)
    x = 20

func()

print(x)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
10
20
\end{dhkzsh}

dㅕ기서 \zsh{global x}는 무엇을 하는 걸까?

많이 하는 오해는 다음과 같다.

\begin{dhksmry}[centered]
global은 지역 변수를 전역 변수로 이동시킨다.
\end{dhksmry}

하지만 정확하지 않다.

\zsh{global x}는 현재 코드 블록에서 \zsh{x}를 지역 이름으로 취급하지 않고, 모듈의 전역 이름으로 취급하도록 지정하는 선언문이다.

즉, \zsh{global}은 객체를 이동시키는 연산이 아니다.

이름의 스코프 판정에 영향을 주는 선언이다.

\begin{dhknote}
\begin{dhksmry}[centered]
실행 과정 분석
\end{dhksmry}
\end{dhknote}

먼저 모듈에서 다음 문장이 실행된다.

\begin{dhkcode}
x = 10
\end{dhkcode}

모듈 네임스페이스의 \zsh{x}가 정수 객체 10을 참조한다.

이후 \zsh{func}가 정의된다.

컴파일 과정에서 다음 선언을 분석한다.

\begin{dhkcode}
global x
\end{dhkcode}

따라서 \zsh{func} 내부의 \zsh{x}는 전역 이름으로 분류된다.

이제 \zsh{func()}가 호출된다.

\begin{dhkcode}
print(x)
\end{dhkcode}

전역 이름 \zsh{x}를 조회하므로 10이 출력된다.

다음 문장이 실행된다.

\begin{dhkcode}
x = 20
\end{dhkcode}

이 대입은 지역 이름을 새로 바인딩하는 것이 아니다.

모듈 전역 네임스페이스의 \zsh{x}를 정수 객체 20에 재바인딩한다.

따라서 함수 호출이 끝난 뒤에도

\begin{dhkcode}
print(x)
\end{dhkcode}

는 20을 출력하는 것이다.

\begin{dhknote}
\begin{dhksmry}[centered]
바인딩 구조
\end{dhksmry}
\end{dhknote}

호출 전:

\begin{dhksmry}
    Global Namespace

    x \ra int(10)
\end{dhksmry}

호출 후:

\begin{dhksmry}
    Global Namespace

    x \ra int(20)
\end{dhksmry}

기존 정수 객체 10이 20으로 변경된 것이 아니다.

전역 이름 \zsh{x}가 새로운 정수 객체를 참조하도록 재바인딩된 것이다.

이 차이는 \zsh{A.1}에서 학습한 이름 바인딩과 동일한 원리다.

\subsubsection{\zsh{global}은 반드시 전역 변수가 이미 존재해야 사용할 수 있을까?}

그렇지는 않다.

다음 코드를 보자.

\begin{dhkcode}
def create_global():
    global message
    message = "Hello"

create_global()

print(message)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
Hello
\end{dhkzsh}

\zsh{global message} 선언 자체가 전역 이름에 객체를 바인딩하는 것은 아니다.

실제로 다음 대입문이 실행될 때

\begin{dhkcode}
message = "Hello"
\end{dhkcode}

모듈의 전역 네임스페이스에 \zsh{message}가 바인딩되는 것이다.

따라서 다음 코드는 다르게 동작한다.

\begin{dhkcode}
def func():
    global message
    print(message)

func()
\end{dhkcode}

현재 모듈에 \zsh{message}가 없고 내장 이름으로도 존재하지 않는 일반적인 상황이라면 \zsh{NameError}가 발생한다.

즉, \zsh{global} 선언이 있다고 해서 그 이름에 자동으로 \zsh{None} 같은 객체가 바인딩되는 것은 아니다.

\subsubsection{\zsh{global}의 범위는 어디까지일까?}

다음 코드를 살펴보자.

\begin{dhkcode}
x = 10

def outer():
    x = 20

    def inner():
        global x
        x = 30

    inner()

    print("outer x:", x)

outer()

print("global x:", x)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
outer x: 20
global x: 30
\end{dhkzsh}

이 결과가 중요한 이유는 \zsh{global}이 가장 가까운 외부 함수의 이름을 의미하지 않기 때문이다.

\zsh{inner}에는 렉시컬 외부 함수인 \zsh{outer}가 존재한다.

그런데 \zsh{global x}는 \zsh{outer}의 \zsh{x}를 대상으로 하지 않는다.

모듈 전역의 \zsh{x}를 대상으로 한다.

따라서 \zsh{inner()}에서 다음 대입문이 실행되면

\begin{dhkcode}
x = 30
\end{dhkcode}

전역 \zsh{x}가 재바인딩 된다.

반면 \zsh{outer}의 지역 \zsh{x}는 여전히 20을 참조하고 있다.

구조를 나타내면 다음과 같다.

\begin{dhkdir}[in=6]
Global Namespace
> x -> 30
> outer
>> Local x -> 20
>> inner
>>> global x
>>>> Global x 참조
\end{dhkdir}

여기서 다음 원칙을 확립할 수 있다.

\zsh{global}은 가장 가까운 외부 스코프를 선택하는 선언이 아니라, 모듈 전역 스코프를 대상으로 하는 선언이다.

\subsubsection{\zsh{global}과 \zsh{nonlocal}의 차이}

\zsh{global}과 함께 반드시 비교해야 하는 선언이 \zsh{nonlocal}이다.

\zsh{nonlocal}의 내부 구조와 클로저 상태 변경은 \zsh{A.5}에서 자세히 다룰 예정이므로, 이번에는 스코프 선택 관점에서만 살펴본다.

\begin{dhkcode}
x = 10

def outer():
    x = 20

    def inner():
        nonlocal x
        x = 30

    inner()

    print("outer x:", x)

outer()

print("global x:", x)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
outer x: 30
global x: 10
\end{dhkzsh}

이번에는 \zsh{inner}에서 \zsh{nonlocal x}를 선언하였다.

이 선언은 현재 함수의 지역 스코프가 아닌, 렉시컬 외부 함수 스코프에 존재하는 \zsh{x} 바인딩을 사용하도록 지정한다.

따라서 \zsh{inner()} 내부의

\begin{dhkcode}
x = 30
\end{dhkcode}

은 \zsh{outer}의 \zsh{x}를 재바인딩한다.

전역 \zsh{x}에는 영향을 주지 않는다.

\begin{dhknote}
\begin{dhksmry}[centered]
global과 nonlocal 비교
\end{dhksmry}
\end{dhknote}

\begin{dhktable}
|구분|global|nonlocal|
|:---|:---|:---|
|대상|	모듈 전역 스코프|	렉시컬 외부 함수 스코프|
|지역 이름 판정|	현재 블록에서 지역 이름으로 취급하지 않음|	현재 블록에서 지역 이름으로 취급하지 않음|
|기존 바인딩 필요 여부|	없어도 선언 가능|	외부 함수 스코프에 기존 바인딩이 필요|
|재바인딩 대상|	전역 이름|	외부 함수의 이름|
|주된 활용|	모듈 수준 상태 변경|	클로저 상태 변경|
\end{dhktable}

여기서 \zsh{nonlocal}의 중요한 제약이 있다.

\begin{dhkcode}
def outer():

    def inner():
        nonlocal x
        x = 10

    inner()
\end{dhkcode}

이 코드는 \zsh{SyntaxError}를 발생시킨다.

왜냐하면 \zsh{inner}를 감싸는 외부 함수 스코프에 \zsh{x}라는 바인딩이 존재하지 않기 때문이다.

반면 \zsh{global x}는 기존 전역 바인딩이 없어도 사용할 수 있었다.

이 차이를 기억해야 한다.

\subsubsection{\zsh{global}은 어디에 선언해야 할까?}

다음 코드를 보자.

\begin{dhkcode}
x = 10

def func():
    print(x)
    global x
\end{dhkcode}

이 코드는 일반적인 Python 컴파일 과정에서 \zsh{SyntaxError}를 발생시킨다.

같은 코드 블록에서 \zsh{global x} 선언보다 앞서 \zsh{x}를 사용했기 때문이다.

따라서 보통 다음처럼 작성해야 한다.

\begin{dhkcode}
x = 10

def func():
    global x

    print(x)
\end{dhkcode}

여기서 \zsh{global}은 함수가 실행되는 동안 특정 시점부터 효력이 발생하는 일반적인 명령문이 아니다.

\begin{dhksmry}[centered]
해당 코드 블록의 이름 해석 방식에 영향을 주는 컴파일러 지시문이다.
\end{dhksmry}

따라서 선언이 함수 본문 전체의 이름 분류와 연결된다는 점을 이해해야 한다.

또한 \zsh{global} 선언은 자신이 포함된 코드 블록에 적용된다.

외부 함수에 \zsh{global x}를 선언했다고 해서 그 내부에 정의된 별도 함수 블록까지 자동으로 같은 선언이 적용되는 것은 아니다.

\subsubsection{이름의 스코프를 직접 확인하기 - \zsh{symtable}}

지금까지 이름의 정적 판정을 설명하였다.

그런데 실제로 Python이 이름을 어떻게 분류하는지 확인할 방법은 없을까?

표준 라이브러리의 \zsh{symtable} 모듈을 활용할 수 있다.

\zsh{symtable}은 Python 소스 코드의 심볼 테이블(Symbol Table) 정보를 분석하는 기능을 제공한다.

다음 코드를 보자.

\begin{dhkcode}
import symtable

source = """
x = 10

def func():
    print(x)
    x = 20
"""

table = symtable.symtable(source, "<string>", "exec")

func_table = next(
    child
    for child in table.get_children()
    if child.get_name() == "func"
)

x_symbol = func_table.lookup("x")

print(x_symbol.is_local())
print(x_symbol.is_global())
print(x_symbol.is_referenced())
print(x_symbol.is_assigned())
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
True
False
True
True
\end{dhkzsh}

여기서 확인할 수 있는 것은 다음과 같다.

\zsh{x}는 \zsh{func} 내부에서 지역 이름으로 분류된다.

또한 읽기 대상으로 참조되고, 대입 대상으로 사용되고 있다.

중요한 점은 이 코드를 실행할 때 분석 대상 문자열의 \zsh{func()}를 호출하지 않았다는 사실이다.

즉, 실제 함수 본문을 실행하지 않고도 이름의 정적 분류를 확인할 수 있다.

이번에는 \zsh{global}을 추가해 보자.

\begin{dhkcode}
import symtable

source = """
x = 10

def func():
    global x
    print(x)
    x = 20
"""

table = symtable.symtable(source, "<string>", "exec")

func_table = next(
    child
    for child in table.get_children()
    if child.get_name() == "func"
)

x_symbol = func_table.lookup("x")

print(x_symbol.is_local())
print(x_symbol.is_global())
print(x_symbol.is_declared_global())
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
False
True
True
\end{dhkzsh}

이번에는 \zsh{x}가 지역 이름이 아니라 명시적으로 선언된 전역 이름으로 분류된다는 사실을 확인할 수 있다.

이것은 \zsh{global}이 실행 시점에 객체를 이동시키는 기능이 아니라 이름 분류를 변경하는 선언이라는 설명과 일치한다.

\subsubsection{바이트 코드로 확인하기 - \zsh{dis}}

한 단계 더 들어가 보자.

Python의 표준 라이브러리 \zsh{dis}를 사용하면 CPython이 함수의 이름 접근을 어떤 바이트코드 명령으로 구현하는지 관찰할 수 있다.

\begin{dhkcode}
import dis

x = 10

def local_func():
    x = 20
    return x


def global_func():
    return x


def declared_global_func():
    global x
    x = 30
    return x


dis.dis(local_func)
dis.dis(global_func)
dis.dis(declared_global_func)
\end{dhkcode}

Python 버전에 따라 정확한 바이트코드 구성과 출력 형식은 달라질 수 있다.

다만 일반적인 CPython에서는 다음과 같은 명령의 차이를 관찰할 수 있다.

\begin{dhktable}
|함수|주요 명령|의미|
|:---|:---|:---|
|local_func|STORE_FAST, LOAD_FAST|지역 이름 바인딩 및 조회|
|global_func|LOAD_GLOBAL|전역·내장 이름 조회|
|declared_global_func|STORE_GLOBAL, LOAD_GLOBAL|전역 이름 바인딩 및 조회|
\end{dhktable}

이 차이는 중요한 사실을 보여준다.

Python이 함수 호출 때마다 모든 이름에 대해 동일한 방식으로 LEGB 검색을 수행하는 것은 아니다.

컴파일 단계에서 이름의 종류를 분석하고, 그결과에 따라서 서로 다른 접근 방식을 사용할 수 있다.

단, 바이트코드는 CPython 버전의 바이트코드 구현을 구분해야 한다.

\subsubsection{\zsh{NameError}와 \zsh{UnboundLocalError}의 차이}

이번에는 두 예외를 비교해 보자.

\begin{dhknote}
\begin{dhksmry}[centered]
사례 1. 이름을 찾을 수 없는 경우
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def func():
    return unknown_name

func()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
NameError
\end{dhkzsh}

\zsh{unknown_name}은 지역 이름으로 바인딩되지 않았고, 외부 함수 스코프나 전역·내장 스코프에서도 찾을 수 없는 일반적인 상황이다.

따라서 \zsh{NameError}가 발생한다.

\begin{dhknote}
\begin{dhksmry}[centered]
사례 2. 지역 이름이지만 아직 바인딩되지 않은 경우
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def func():
    print(x)
    x = 10

func()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
UnboundLocalError
\end{dhkzsh}

여기서는 \zsh{x}가 지역 이름으로 판정되었지만 읽는 시점에 바인딩되어 있지 않다.

따라서 \zsh{UnboundLocalError}가 발생한다.

\begin{dhknote}
\begin{dhksmry}[centered]
사례 3. 외부 함수의 자유 변수가 아직 바인딩되지 않은 경우
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def outer():

    def inner():
        return x

    result = inner()

    x = 10

    return result


outer()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
NameError
\end{dhkzsh}

이 경우는 앞의 두 사례와 구분해야 한다.

\zsh{inner} 내부의 \zsh{x}는 지역 이름이 아니다.

\zsh{outer}의 렉시컬 스코프에 존재하는 자유 변수다.

하지만 \zsh{inner()}를 호출하는 시점에는 \zsh{outer}의 \zsh{x = 10}이 아직 실행되지 않았다.

따라서 외부 스코프의 자유 변수 바인딩을 읽을 수 없어 \zsh{NameError}가 발생한다.

CPython에서는 일반적으로 다음과 유사한 메시지를 볼 수 있다.

\begin{dhkzsh}
NameError: cannot access free variable 'x' 
where it is not associated with a value in enclosing scope
\end{dhkzsh}

여기서 중요한 점은 외부 함수의 자유 변수가 바인딩되지 않은 경우와 현재 함수의 지역 변수가 바인딩되지 않은 경우의 예외 종류가 다를 수 있다는 것이다.

\begin{dhknote}
\begin{dhksmry}[centered]
비교 정리
\end{dhksmry}
\end{dhknote}

\begin{dhktable}
|상황|이름 분류|대표적인 예외|
|이름을 어떤 접근 가능한 스코프에서도 찾을 수 없음|전역·내장 이름 등|NameError|
|현재 함수의 지역 이름이 아직 바인딩되지 않음|Local|UnboundLocalError|
|외부 함수의 자유 변수 바인딩이 아직 존재하지 않음|Free Variable|NameError|
\end{dhktable}

\zsh{UnboundLocalError}는 \zsh{NameError}의 하위 클래스다.

\begin{dhkcode}
print(issubclass(UnboundLocalError, NameError))
\end{dhkcode}

출력:

\begin{dhkzsh}
True
\end{dhkzsh}

따라서 \zsh{except NameError}는 \zsh{UnboundLocalError}도 포착할 수 있다.

하지만 두 예외가 발생하는 원인은 구분해야 한다.

\subsubsection{이름 탐색과 속성 탐색은 다르다}

기존 클래스 객체 모델과 연결해 보자.

\begin{dhkcode}
class Example:
    x = 100

    def method(self):
        return x


obj = Example()
\end{dhkcode}

여기서 \zsh{method()} 내부의 \zsh{x}는 \zsh{Example.x}를 자동으로 참조하지 않는다.

일반적인 메서드의 이름 탐색에서 클래스 네임스페이스가 외부 함수 스코프처럼 포함되지 않기 때문이다.

반면 다음 코드는 정상적으로 동작한다.

\begin{dhkcode}
class Example:
    x = 100

    def method(self):
        return self.x


obj = Example()

print(obj.method())
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
100
\end{dhkzsh}

왜 그럴까?

\begin{dhkcode}
return self.x
\end{dhkcode}

는 두 단계로 평가된다.

먼저 \zsh{self}라는 이름을 현재 함수의 지역 스코프에서 조회한다.

일반적인 인스턴스 메서드 호출에서는 \zsh{self}가 인스턴스 객체를 참조한다.

그다음 그 인스턴스 객체에서 \zsh{x} 속성을 탐색한다.

이 속성 탐색은 LEGB가 아니라 객체의 속성 접근 규칙에 따라 처리된다.

일반적인 사용자 정의 인스턴스에서는 인스턴스 네임스페이스, 클래스와 상속 계층, 디스크립터 등이 관여할 수 있다.

따라서 다음 두 표현식은 전혀 다른 메커니즘이다.

\begin{dhktable}
|표현식|메커니즘|
|:---|:---|
|x|이름 탐색(Name Resolution)|
|self.x|self 이름 탐색 후 속성 탐색(Attribute Lookup)|
|Example.x|Example 이름 탐색 후 클래스 객체의 속성 탐색|
\end{dhktable}

이 구분은 PyTorch의 \zsh{nn.Module}을 이해할 때도 중요하다.

\subsubsection{실전 응용 - PyTorch에서의 이름 탐새고가 속성 탐색}

다음 예제를 살펴보자.

\begin{dhkcode}
import torch
from torch import nn


class MyModel(nn.Module):
    def __init__(self):
        super().__init__()

        self.linear = nn.Linear(3, 2)

    def forward(self, x):
        return self.linear(x)


model = MyModel()

x = torch.randn(1, 3)

print(model(x).shape)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
torch.Size([1, 2])
\end{dhkzsh}

이 코드는 기존에 학습한 \zsh{nn.Module} 객체 모델과 연결된다.

\zsh{forward()} 내부의 다음 표현식을 보자.

\begin{dhkcode}
self.linear(x)
\end{dhkcode}

여기에는 여러 단계가 존재한다.

\begin{dhknote}
\begin{dhksmry}[centered]
1. self 이름 탐색
\end{dhksmry}
\end{dhknote}

\zsh{self}는 \zsh{forward()} 호출의 지역 이름이다.

따라서 Local 스코프에서 조회된다.

\begin{dhknote}
\begin{dhksmry}[centered]
2. self.linear 속성 탐색
\end{dhksmry}
\end{dhknote}

이제 \zsh{self}가 참조하는 \zsh{MyModel} 인스턴스에서 \zsh{linear} 속성을 탐색한다.

PyTorch의 \zsh{nn.Module}은 하위 모듈 등록과 조회를 위해 일반적인 Python 객체 모델을 확장하고 있다.

\zsh{self.linear = nn.Linear(3,2)}가 실행되면 \zsh{nn.Module}의 등록 메커니즘을 통해 하위 모듈이 관리된다.

이후 \zsh{self.linear}에 접근할 때는 \zsh{nn.Module}이 제공하는 속성 조회 동작이 관여할 수 있다.

\begin{dhknote}
\begin{dhksmry}[centered]
3. self.linear(x) 호출
\end{dhksmry}
\end{dhknote}

조회된 \zsh{nn.Linear} 인스턴스는 호출 가능한 객체다.

따라서 \zsh{__call__}을 통한 모듈 호출 과정이 진행되고, 최종적으로 선형 변환이 수행된다.

여기서 LEGB가 담당하는 것은 \zsh{self}라는 이름을 조회하는 부분이다.

\zsh{linear}를 찾는 과정은 객체의 속성 탐색이다.

이 둘을 구별해야 Python의 일반적인 스코프 규칙과 PyTorch가 확장한 객체 동작을 혼동하지 않게 된다.

\subsubsection{경계 조건 - LEGB만으로 모든 이름 접근을 설명할 수 있을까?}

LEGB는 일반적인 함수 이름 탐색을 이해하는 데 유용하지만, Python의 모든 이름 접근을 단순한 네 단계 검색으로 환원할 수는 없다.

대표적인 예외와 주의점을 정리해 보자.

\begin{dhknote}
\begin{dhksmry}[centered]
1. 클래스 본문은 일반적인 함수 스코프와 다르다
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x = 10

class Example:
    x = 20

    def method(self):
        return x
\end{dhkcode}

\zsh{method()}의 \zsh{x}는 일반적인 상황에서 클래스 본문의 \zsh{x = 20}을 렉시컬 외부 함수 변수처럼 사용하지 않는다.

모듈 전역의 \zsh{x = 10}을 조회한다.

클래스 본문에는 별도의 이름 해석 규칙이 존재하기 때문이다.

\begin{dhknote}
\begin{dhksmry}[centered]
2. 컴프리헨션은 별도의 스코프 규칙을 갖는다
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x = 100

values = [x for x in range(3)]

print(values)
print(x)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
[0, 1, 2]
100
\end{dhkzsh}

Python 3에서 리스트 컴프리헨션의 반복 변수 \zsh{x}는 일반적으로 바깥 스코프의 \zsh{x}를 덮어쓰지 않는다.

다만 컴프리헨션의 종류와 Python 버전에 따라 내부 구현 및 세부 규칙이 달라질 수 있다.

\begin{dhknote}
\begin{dhksmry}[centered]
3. exec()는 일반적인 정적 이름 바인딩과 구분해야 한다
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def func():
    exec("x = 10")
\end{dhkcode}

\zsh{exec()}이 문자열을 실행한다고 해서 컴파일된 \zsh{func}의 지역 이름 분류가 그 문자열에 맞춰 다시 결정되는 것은 아니다.

특히 최적화된 ㅎ마수 지역 스코프에서 \zsh{exec()}로 생성한 이름을 일반적인 지역 변수처럼 접근할 수 있다고 가정하면 안 된다.

\begin{dhknote}
\begin{dhksmry}[centered]
4. del도 바인딩 상태에 영향을 준다
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def func():
    x = 10
    del x
    return x


func()
\end{dhkcode}

예상 결과:

\begin{dhkzsh}
UnboundLocalError
\end{dhkzsh}

\zsh{x}는 지역 이름으로 판정되어 있고, 처음에는 정수 객체 10에 바인딩된다.

하지만 \zsh{del x}가 실행되면서 그 지역 이름의 바인딩이 제거된다.

이후 \zsh{return x}에서 다시 조회하려고 하면 바인딩된 객체가 없으므로 예외가 발생한다.

여기서 \zsh{del x}는 정수 객체 10을 직접 파괴하는 명령이 아니라 이름의 바인딩을 제거하는 연산이라는 점도 기억해야 한다.

\subsubsection{종합 예제 - 이름 분류와 실행 상태 추적}

이번 학습의 핵심 개념을 하나의 코드에 통합해 보자.

\begin{dhkcode}
x = 10


def outer():
    x = 20
    y = 30

    def inner():
        global x
        nonlocal y

        x = 100
        y = 200

        return x, y

    result = inner()

    print("outer x:", x)
    print("outer y:", y)

    return result


result = outer()

print("global x:", x)
print("result:", result)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
outer x: 20
outer y: 200
global x: 100
result: (100, 200)
\end{dhkzsh}

이제 실행 과정을 순서대로 분석해 보자.

\begin{dhknote}
\begin{dhksmry}[centered]
1. 모듈 전역 이름 바인딩
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x = 10
\end{dhkcode}

전역 이름 \zsh{x}가 정수 객체 10을 참조한다.

\begin{dhknote}
\begin{dhksmry}[centered]
2. outer() 호출
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x = 20
y = 30
\end{dhkcode}

현재 \zsh{outer()} 호출의 지역 스코프에 \zsh{x}와 \zsh{y}가 바인딩된다.

\begin{dhknote}
\begin{dhksmry}[centered]
3. inner 함수 객체 생성
\end{dhksmry}
\end{dhknote}

\zsh{inner} 함수 객체가 생성된다.

이 함수의 본문에는 다음 선언이 있다.

\begin{dhkcode}
global x
nonlocal y
\end{dhkcode}

따라서 \zsh{inner}의 \zsh{x}는 전역 이름으로, \zsh{y}는 외부 함수 스코프의 이름으로 분류된다.

\begin{dhknote}
\begin{dhksmry}[centered]
4. inner() 호출
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x = 100
\end{dhkcode}

전역 \zsh{x}가 정수 객체 100에 재바인딩된다.

다음으로

\begin{dhkcode}
y = 200
\end{dhkcode}

외부 함수 \zsh{outer}의 \zsh{y}가 정수 객체 200에 재바인딩된다.

여기서 \zsh{outer}의 지역 \zsh{x}는 변경되지 않는다.

\begin{dhknote}
\begin{dhksmry}[centered]
5. 반환
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
return x, y
\end{dhkcode}

현재 전역 \zsh{x}와 외부 함수의 \zsh{y}를 조회한다.

각각 100, 200을 얻고 튜플 객체를 구성해 반환한다.

\begin{dhknote}
\begin{dhksmry}[centered]
6. outer()의 나머지 분문 실행
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
print("outer x:", x)
\end{dhkcode}

여기서 \zsh{x}는 \zsh{outer}의 지역 이름으로 20이 출력된다.

\begin{dhkcode}
print("outer y:", y)
\end{dhkcode}

\zsh{inner()}에서 \zsh{nonlocal y}를 통해 외부 함수의 바인딩을 변경했으므로 200이 출력된다.

\begin{dhknote}
\begin{dhksmry}[centered]
7. 모듈 코드 실행
\end{dhksmry}
\end{dhknote}

마지막으로 전역 \zsh{x}는 100을 참조하고 있다.

그리고 \zsh{result}에는 \zsh{(100, 200)} 튜플 객체가 바인딩된다.

이 예제는 다음 네 가지를 동시에 보여준다.

\begin{dhksmry}
    - Local 이름과 Global 이름은 같은 철자를 사용해도
      서로 다른 바인딩일 수 있다.

    - global은 모듈 전역 이름을 대상으로 한다.

    - nonlocal은 렉시컬 외부 함수의 이름을 대상으로 한다.

    - 함수의 실행 순서와 이름의 스코프 판정은 구별해야 한다.
\end{dhksmry}

\subsubsection{핵심 정리와 판단 기준}

이번 학습에서 반드시 확립해야 하는 판단 기준은 다음과 같다.

\begin{dhknote}
\begin{dhksmry}[centered]
첫째, 이름을 읽는다고 해서 무조건 LEGB 전체를
순차 검색하는 것은 아니다.
\end{dhksmry}
\end{dhknote}

Python은 컴파일 과정에서 함수 블록의 이름 사용을 분석하고, 이름 종류를 판정한다.

따라서 지역 이름으로 판정된 이름이 바인딩되지 않았다고 해서 자동으로 전역 이름을 사용하는 것은 아니다.

\begin{dhknote}
\begin{dhksmry}[centered]
둘째, 이름의 분류와 객체의 바인딩 상태는 서로 다르다.
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def func():
    print(x)
    x = 10
\end{dhkcode}

여기서 \zsh{x}는 지역 이름이지만, \zsh{print(x)} 실행 시점에는 아직 객체가 바인딩되어 있지 않다.

그래서 \zsh{UnboundLocalError}가 발생한다.

\begin{dhknote}
\begin{dhksmry}[centered]
셋째, global은 객체를 이동시키지 않는다.
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
global x
\end{dhkcode}

는 해당 코드 블록에서 \zsh{x}를 전역 이름으로 취급하도록 지정하는 선언이다.

실제 객체 바인딩은 대입문 등이 실행될 때 발생한다.

\begin{dhknote}
\begin{dhksmry}[centered]
넷째, global과 nonlocal은 대상 스코프가 다르다.
\end{dhksmry}
\end{dhknote}

\zsh{global}은 모듈 전역 스코프를 대상으로 하고, \zsh{nonlocal}은 렉시컬 외부 함수 스코프의 기존 바인딩을 대상으로 한다.

\begin{dhknote}
\begin{dhksmry}[centered]
다섯째, 이름 탐색과 속성 탐색을 구분해야 한다.
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
x
\end{dhkcode}

와

\begin{dhkcode}
self.x
\end{dhkcode}

는 서로 다른 메커니즘으로 처리된다.

전자는 이름 탐색이고, 후자는 \zsh{self} 이름을 조회한 뒤 객체의 속성을 탐색하는 표현식이다.
