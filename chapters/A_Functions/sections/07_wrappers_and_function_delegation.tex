\subsection{\zsh{Wrapper}의 생성, 인수 전달과 반환}

Wrapper Function · Argument Binding · *args · **kwargs · Return Value · Exception Propagation

\subsubsection{이전 학습과의 연결}

\zsh{A.6}에서는 데코레이터(Decorator)의 본질이 특별한 함수 수정 기능이 아니라, 함수 객체를 전달하고 데코레이터의 반환 객체를 원래 이름에 다시 바인딩하는 과정이라는 사실을 학습했다.

다음 두 코드는 단일 함수 데코레이터의 일반적인 의미에서 대응한다.

\begin{dhkcode}
@decorator
def add(a, b):
    return a + b
\end{dhkcode}

\begin{dhkcode}
def add(a, b):
    return a + b

add = decorator(add)
\end{dhkcode}

그리고 \zsh{decorator}가 새로운 \zsh{wrapper} 함수 객체를 반환한다면, 데코레이션 이후 \zsh{add}라는 이름은 원본 함수가 아니라 \zsh{wrapper}를 참조하게 된다.

그렇다면 다음 문제가 발생한다.

원본 함수 \zsh{add(a, b)}처럼 두 인수를 받도록 정의되어 있는데, \zsh{wrapper}는 어떤 인수를 받아야 할까?

원본 함수가 반환한 객체는 어떻게 호출자에게 전달될까?

원본 함수에서 예외가 발생하면 \zsh{wrapper}의 실행은 어떻게 될까?

이번 학습은 이러한 문제를 Python의 일반적인 함수 호출과 인수 바인딩 규칙으로 설명하는 것이 목표다.

\begin{dhktable}
|이전 단원|	이번 단원|
|:---|:---|
|데코레이터가 언제 적용되는가?|	wrapper는 언제 호출되는가?|
|원본 함수 객체는 어디에 유지되는가?|	wrapper는 원본 함수를 어떻게 호출하는가?|
|@decorator는 어떤 객체를 반환하는가?|	반환값과 예외는 호출자에게 어떻게 전달되는가?|
|함수 이름이 어떤 객체에 재바인딩되는가?|	각 호출에서 어떤 지역 네임스페이스가 만들어지는가?|
\end{dhktable}

여기서 가장 중요한 원리는 다음이다.

\begin{dhksmry}[centered]
데코레이터가 적용되더라도 

Python의 일반적인 함수 호출 규칙이 바뀌는 것은 아니다.

단지 호출 경로에 새로운 함수 객체가 추가되는 것이다.
\end{dhksmry}

\subsubsection{Wrapper의 정확한 정의와 역할}

Wrapper는 다른 함수나 호출 가능한 객체의 호출을 감싸는 역할을 수행하는 함수다.

Python에 별도의 \zsh{wrapper} 타입이 존재하는 것은 아니다.

일반적인 함수 객체가 다른 함수를 호출하는 구조로 작성되었을 때 그 역할을 wrapper라고 부르는 것이다.

대표적인 구조는 다음과 같다.

\begin{dhkcode}
def decorator(func):

    def wrapper(*args, **kwargs):
        # 원본 함수 호출 전 처리

        result = func(*args, **kwargs)

        # 원본 함수 호출 후 처리

        return result

    return wrapper
\end{dhkcode}

이 코드를 객체 모델 관점에서 구분하면 다음과 같다.

\begin{dhksmry}
    - decorator는 원본 함수 객체를 전달받는 함수다.

    - func는 원본 함수 객체를 참조하는 외부 함수의 매개변수다.

    - wrapper는 데코레이터 호출 중 새로 생성되는 함수 객체다.

    - args, kwargs는 wrapper가 호출될 때 바인딩되는 지역 매개변수다.

    - func(*args, **kwargs)는 원본 함수 객체를 실제로 호출하는
      표현식이다.

    - result는 원본 함수가 반환한 객체를 참조하는 지역 이름이다.
\end{dhksmry}

이 관계를 시점별로 구별해야 한다.


\begin{dhknote}
\begin{dhksmry}[centered]
정의 시점의 객체 관계
\end{dhksmry}
\end{dhknote}

\begin{dhkgraph}[uniform]
node n1 (1,1) :: 함수 이름 add
node n2 (1,2) [accent] :: wrapper 함수 객체
node n3 (2,2) :: 클로저 셀 func
node n4 (3,2) [accent] :: 원본 add 함수 객체

edge n1 -> n2
edge n2 -> n3
edge n3 -> n4
\end{dhkgraph}

\begin{dhknote}
\begin{dhksmry}[centered]
호출 시점의 실행 흐름
\end{dhksmry}
\end{dhknote}

\begin{dhkgraph}[uniform]
node n1 (1,1) :: add(2, 3)
node n2 (1,2) :: wrapper 호출
node n3 (1,3) :: 원본 호출
edge n1 -> n2
edge n2 -> n3

caption :: 객체의 참조 관계와 실제 함수 호출 순서는 구별해야 한다. // wrapper가 원본 함수를 참조하고 있다는 사실만으로 원본 함수가 실행되지는 않는다.
\end{dhkgraph}

\subsubsection{최소 실행 예제 - 정의 시점과 호출 시점}

먼저 하나의 완전한 예제를 살펴보자.

\begin{dhkcode}
def trace(func):
    print("데코레이터 적용:", func.__name__)

    def wrapper(*args, **kwargs):
        print("호출 전:", args, kwargs)

        result = func(*args, **kwargs)

        print("호출 후:", result)

        return result

    return wrapper


@trace
def calculate(a, b, *, scale=1):
    return (a + b) * scale


print("함수 정의 완료")

answer = calculate(2, 3, scale=4)

print("최종 결과:", answer)
\end{dhkcode}

예상 실행 결과:

\begin{dhkzsh}
데코레이터 적용: calculate
함수 정의 완료
호출 전: (2, 3) {'scale': 4}
호출 후: 20
최종 결과: 20
\end{dhkzsh}

이 코드는 두 단계로 나누어 분석해야 한다.

\begin{dhknote}
\begin{dhksmry}[centered]
1. 함수 정의문이 실행될 때
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
@trace
def calculate(a, b, *, scale=1):
    return (a + b) * scale
\end{dhkcode}

원본 \zsh{calculate} 함수 객체가 생성된다.

그 함수 객체가 \zsh{trace}에 전달되고, \zsh{trace} 내부에서 \zsh{wrapper} 함수 객체가 생성된다.

\zsh{trace}가 반환한 \zsh{wrapper}가 모듈 이름 \zsh{calculate}에 바인딩된다.

이 시점에는 \zsh{wrapper}의 본문이 실행되지 않았다.

따라서 출력은 다음 한 줄뿐이다.

\begin{dhkzsh}
데코레이터 적용: calculate
\end{dhkzsh}

\begin{dhknote}
\begin{dhksmry}[centered]
2. calculate(2, 3, scale=4)가 호출될 때
\end{dhksmry}
\end{dhknote}

이제 모듈 이름 \zsh{calculate}는 \zsh{wrapper} 함수 객체를 참조하고 있다.

따라서 호출 표현식은 실제로 다음 함수의 호출이 된다.

\begin{dhkcode}
def wrapper(*args, **kwargs):
    ...
\end{dhkcode}

호출 과정에서 \zsh{wrapper}의 지역 매개변수는 다음 객체에 바인딩된다.

\begin{dhkzsh}
args = (2, 3)
kwargs = {"scale": 4}
\end{dhkzsh}

이것은 호출 결과를 설명하기 위한 표현이다.

Python이 실제로 이 두 대입문을 소스 코드처럼 실행한다는 뜻은 아니다.

이후 다음 표현식이 평가된다.

\begin{dhkcode}
func(*args, **kwargs)
\end{dhkcode}

\zsh{func}은 클로저 셀을 통해 원본 \zsh{calculate} 함수 객체를 참조한다.

따라서 원본 함수가 호출되고 다음과 같이 인수가 바인딩된다.

\begin{dhktable}
|원본 매개변수|	바인딩된 객체|	전달 방식|
|:---|:---|:---|
|a|	2|	위치 인수|
|b|	3|	위치 인수|
|scale|	4|	키워드 인수|
\end{dhktable}

원본 함수는 \zsh{(2 + 3) * 4}를 계산해 정수 객체 20을 반환한다.

그 객체가 \zsh{wrapper}의 지역 이름 \zsh{result}에 바인딩되고,

다시 \zsh{return result}를 통해 최종 호출자에게 전달되는 것이다.

이제 이 과정을 인수 바인딩, 반환, 예외의 세 부분으로 나누어 더 깊이 분석해 보자.

\subsubsection{\zsh{*args}와 \zsh{**kwargs}의 정확한 역할}

다음 함수 정의를 살펴보자.

\begin{dhkcode}
def wrapper(*args, **kwargs):
    return func(*args, **kwargs)
\end{dhkcode}

여기서 \zsh{*args}와 \zsh{**kwargs}는 함수 정의 위치와 함수 호출 위치에서 서로 다른 역할을 한다.

\begin{dhktable}
|위치|	표현식|	의미|
|:---|:---|:---|
|함수 정의|	def wrapper(*args, **kwargs)|	전달받은 위치 인수와 키워드 인수를 수집|
|함수 호출|	func(*args, **kwargs)|	저장된 객체들을 위치 인수와 키워드 인수로 펼쳐 전달|
\end{dhktable}

같은 기호를 사용하지만 동작은 반대 방향이다.

\begin{dhknote}
\begin{dhksmry}[centered]
1. Wrapper에서 인수 수집
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def inspect_call(func):

    def wrapper(*args, **kwargs):
        print("args:", args)
        print("kwargs:", kwargs)

        return func(*args, **kwargs)

    return wrapper


@inspect_call
def add(a, b):
    return a + b


print(add(10, b=20))
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
args: (10,)
kwargs: {'b': 20}
30
\end{dhkzsh}

\zsh{add(10, b=20)}을 호출하면 실제로는 \zsh{wrapper}가 호출된다.

\zsh{wrapper}의 매개변수 바인딩 결과는 다음과 같다.

\begin{dhkzsh}
args = (10,)
kwargs = {"b": 20}
\end{dhkzsh}

\zsh{args}는 튜플 객체를, \zsh{kwargs}는 딕셔너리 객체를 참조한다.

이때 원본 \zsh{add}의 매개변수 \zsh{a}, \zsh{b}에 아직 인수가 바인딩된 것은 아니다.

현재 실행중인 함수는 \zsh{wrapper}이므로, 먼저 \zsh{wrapper}의 매개변수 바인딩이 발생하는 것이다.

\begin{dhknote}
\begin{dhksmry}[centered]
2. 원본 함수 호출에서 인수 펼치기
\end{dhksmry}
\end{dhknote}

이후 다음 문장이 실행된다.

\begin{dhkcode}
return func(*args, **kwargs)
\end{dhkcode}

이 호출은 현재 예제에서 다음과 같은 호출과 대응한다.

\begin{dhkcode}
func(10, b=20)
\end{dhkcode}

이제 원본 \zsh{add}의 매개변수 바인딩이 수행된다.

\begin{dhkbranch}[in=8]
node main :: wrapper 호출
branchline main -> a1 :: args -> (10,)
stop a1
branchline main -> a2 :: kwargs -> {'b': 20}
stop a2
arrow main
node main :: func(*args, **kwargs)
arrow main
node main :: 원본 add 호출
branchline main -> a3 :: a -> int(10)
stop a3
handoff main -> a4 :: b -> int(20)
\end{dhkbranch}

여기서 인수 전달이 두 번 발생한다는 사실이 중요하다.

첫 번째는 호출자에서 \zsh{wrapper}로, 두 번째는 \zsh{wrapper}에서 원본 함수로 전달되는 과정이다.

다만 이것이 인수 객체 자체를 두 번 복사한다는 뜻은 아니다.

각 함수 호출에서 새로운 매개변수 바인딩이 형성되는 것이다.

\subsubsection{원본 함수의 매개변수 규칙은 그대로 적용된다}

\zsh{*args}와 \zsh{**kwargs}를 사용하면 \zsh{wrapper}가 다양한 형태의 호출을 받아들일 수 있다.

그렇다고 원본 함수의 매개변수 규칙까지 사라지는 것은 아니다.

다음 코드를 살펴보자.

\begin{dhkcode}
def relay(func):

    def wrapper(*args, **kwargs):
        print("wrapper:", args, kwargs)
        return func(*args, **kwargs)

    return wrapper


@relay
def formula(a, /, b, *, c=0):
    return a + b + c


print(formula(1, b=2, c=3))

try:
    formula(a=1, b=2, c=3)
except TypeError as error:
    print(type(error).__name__)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
wrapper: (1,) {'b': 2, 'c': 3}
6
wrapper: () {'a': 1, 'b': 2, 'c': 3}
TypeError
\end{dhkzsh}

왜 첫 번째 호출은 성공하고 두 번째 호출은 실패할까?

원본 함수의 정의를 다시 보자.

\begin{dhkcode}
def formula(a, /, b, *, c=0):
    return a + b + c
\end{dhkcode}

\zsh{a}는 위치 전용 매개변수(Positional-only Parameter)다.

\zsh{b}는 위치 또는 키워드로 전달할 수 있는 매개변수이고, \zsh{c}는 키워드 전용 매개변수(Keyword-only Parameter)다.

첫 번째 호출은 원본 함수의 규칙을 만족한다.

\begin{dhkcode}
formula(1, b=2, c=3)
\end{dhkcode}

반면 두 번째 호출은 다음과 같다.

\begin{dhkcode}
formula(a=1, b=2, c=3)
\end{dhkcode}

\zsh{wrapper}는 이 호출을 받아들일 수 있다.

모든 키워드 인수를 \zsh{kwargs}에 수집하면 되기 때문이다.

하지만 원본 함수에 전달하는 순간 문제가 발생한다.

\begin{dhkcode}
func(*args, **kwargs)
\end{dhkcode}

원본 \zsh{formula}는 \zsh{a}를 키워드 인수로 받는 것을 허용하지 않는다.

따라서 원본 함수의 인수 바인딩 단계에서 \zsh{TypeError}가 발생한다.

이 결과로 다음 원리를 확립할 수 있다.

\begin{dhksmry}[centered]
Wrapper가 호출을 수용할 수 있다는 사실과

원본 함수가 그 호출을 수용할 수 있다는 사실은 서로 다르다.
\end{dhksmry}

\zsh{*args}, \zsh{**kwargs}는 인수를 유연하게 전달하는 수단이지, 원본 함수의 매개변수 규칙을 무효화하는 장치가 아니다.

\subsubsection{기본 인수(Default Argument)}는 어디에서 적용될까?

다음 코드를 보자.

\begin{dhkcode}
def relay(func):

    def wrapper(*args, **kwargs):
        print("wrapper:", args, kwargs)
        return func(*args, **kwargs)

    return wrapper


@relay
def greet(name="Kim"):
    return f"Hello, {name}"


print(greet())
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
wrapper: () {}
Hello, Kim
\end{dhkzsh}

여기서 흥미로운 점이 있다.

\zsh{wrapper}의 \zsh{args}와 \zsh{kwargs}는 모두 비어 있다.

그런데 원본 함수에서는 \zsh{name}이 \zsh{"Kim"}에 바인딩된다.

왜 이런 결과가 발생할까?

기본 인수는 원본 함수 객체의 매개변수 정의에 속하기 때문이다.

원본 \zsh{greet} 함수 객체는 정의될 때 기본 인수 객체를 보관한다.

\zsh{wrapper}가 다음 호출을 수행하면

\begin{dhkcode}
func()
\end{dhkcode}

원본 함수의 인수 바인딩 과정에서 생략된 \zsh{name}에 기본 인수 객체가 사용된다.

따라서 기본 인수를 \zsh{wrapper}가 미리 채워서 전달할 필요는 없다.

다만 \zsh{wrapper}가 인수를 수정하거나 기본값을 별도로 적용하는 구현이라면 실제 동작은 달라질 수 있다.

\begin{dhknote}
\begin{dhksmry}[centered]
인수 객체의 동일성
\end{dhksmry}
\end{dhknote}

또 하나 중요한 점이 있다.

\zsh{wrapper}가 인수를 수집하고 다시 펼친다고 해서 인수 객체가 자동으로 복사되는 것은 아니다.

\begin{dhkcode}
def relay(func):

    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper


@relay
def modify(values):
    values.append(10)
    return values


data = []

result = modify(data)

print(data)
print(result is data)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
[10]
True
\end{dhkzsh}

호출자, \zsh{wrapper}, 원본 함수는 서로 다른 지역 이름을 사용할 수 있지만, 이 예제에서 모두 같은 리스트 객체를 참조한다.

따라서 원본 함수가 리스트를 변경하면 호출자의 \zsh{data}에서도 변경된 상태를 관찰할 수 있다.

이것은 데코레이터의 특별한 규칙이 아니라 \zsh{A.1}에서 학습한 Python의 일반적인 객체 전달 원리다.

\subsubsection{\zsh{Wrapper}의 시그니처(Signature)와 실제 호출 계약}

다음 코드를 살펴보자.

\begin{dhkcode}
def decorator(func):

    def wrapper():
        return func()

    return wrapper


@decorator
def add(a, b):
    return a + b


add(10, 20)
\end{dhkcode}

이 코드는 \zsh{TypeError}를 발생시킨다.

원본 \zsh{add}에 인수를 전달하기도 전에 오류가 발생하는 것이다.

왜냐하면 현재 \zsh{add}라는 이름이 참조하는 함수 객체는 다음과 같기 때문이다.

\begin{dhkcode}
def wrapper():
    return func()
\end{dhkcode}

\zsh{wrapper}는 위치 인수를 받을 매개변수를 정의하지 않았다.

따라서 \zsh{add(10, 20)} 호출에서 \zsh{wrapper}의 인수 바인딩이 실패한다.

여기서 중요한 점은 호출 대상 객체의 실제 시그니처가 먼저 적용된다는 사실이다.

다음과 같이 작성하면 이 문제를 해결할 수 있다.

\begin{dhkcode}
def decorator(func):

    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper
\end{dhkcode}

그러나 이 방법에도 한계가 있다.

원본 함수의 시그니처가

\begin{dhkcode}
def add(a: int, b: int) -> int:
    ...
\end{dhkcode}

라고 하더라도 \zsh{wrapper}의 실제 정의는

\begin{dhkcode}
def wrapper(*args, **kwargs):
    ...
\end{dhkcode}

이다.

따라서 데코레이션 후 함수 객체의 메타데이터와 시그니처를 어떻게 보존할지 별도로 고려해야 한다.

이 문제는 다음 \zsh{A.8}의 \zsh{functools.wraps}와

\zsh{inspect.signature()}에서 다룰 것이다.

\subsubsection{반환값 전달 - \zsh{return func()}와 \zsh{func()}의 차이}

이번 학습에서 인수 전달만큼 중요한 것이 반환값이다.

다음 세 표현식을 비교해 보자.

\begin{dhkcode}
return func

return func()

func()
\end{dhkcode}

세 표현식은 서로 다른 동작을 수행한다.

\begin{dhknote}
\begin{dhksmry}[centered]
사례 1. return func
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def original():
    return 42


def wrapper():
    return original


result = wrapper()

print(result is original)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
True
\end{dhkzsh}

\zsh{wrapper()}는 원본 함수 객체를 반환한다.

원본 함수의 본문은 실행되지 않는다.

\begin{dhknote}
\begin{dhksmry}[centered]
사례 2. return func()
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def original():
    return 42


def wrapper():
    return original()


result = wrapper()

print(result)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
42
\end{dhkzsh}

이번에는 원본 함수가 호출된다.

그 호출 결과인 정수 객체 42가 \zsh{wrapper}의 반환값으로 전달된다.

\begin{dhknote}
\begin{dhksmry}[centered]
사례 3. func()만 실행
\end{dhksmry}
\end{dhknote}

\begin{dhkcode}
def original():
    return 42


def wrapper():
    original()


result = wrapper()

print(result)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
None
\end{dhkzsh}

이번에는 원본 함수가 실행되고 42를 반환한다.

하지만 \zsh{wrapper}는 그 반환값을 다시 반환하지 않는다.

따라서 \zsh{wrapper}본문의 실행이 끝나면 \zsh{None}이 반환된다.

이를 비교하면 다음과 같다.

\begin{dhktable}
|표현식|	원본 함수 호출|	wrapper의 반환값|
|:---|:---|:---|
|return func|	호출하지 않음|	원본 함수 객체|
|return func()|	호출함|	원본 함수의 반환 객체|
|func()|	호출함|	명시적 반환이 없다면 None|
\end{dhktable}

여기서 중요한 결론은 다음과 같다.

Wrapper가 원본 함수를 호출했다는 사실만으로 원본 함수의 반환값이 호출자에게 전달되는 것은 아니다.

Wrapper는 독립적인 함수이므로 자신의 \zsh{return} 규칙을 따르기 때문이다.

\subsubsection{반환갑스이 객체 동일성은 유지될까?}

이번에는 원본 함수가 리스트 객체를 반환하는 경우를 살펴보자.

\begin{dhkcode}
def decorator(func):

    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        return result

    return wrapper


@decorator
def create_list():
    return [10, 20]


result = create_list()

original = create_list.__closure__[0].cell_contents

print(type(result))
print(result)
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
<class 'list'>
[10, 20]
\end{dhkzsh}

여기서 \zsh{result}는 원본 함수가 생성한 리스트 객체를 참조한다.

Wrapper의 \zsh{return result}는 그 객체를 다시 반환한다.

새로운 리스트 객체를 복사해서 생성하는 것이 아니다.

이 관계를 더 명확하게 확인하려면 \zsh{wrapper} 내부에서 반환 객체를 따로 보관해 볼 수 있다.

\begin{dhkcode}
def decorator(func):
    observed = []

    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)

        observed.append(result)

        return result

    return wrapper, observed


def create_list():
    return [10, 20]


wrapped, observed = decorator(create_list)

result = wrapped()

print(result is observed[0])
\end{dhkcode}

예상 출력:

\begin{dhkzsh}
True
\end{dhkzsh}

원본 함수가 반환한 리스트 객체와 최종 호출자가 받은 리스트 객체가 동일하다는 사실을 확인할 수 있다.

이 원리는 PyTorch의 Tensor 객체를 반환하는 함수에도 적용된다.

예를 들어 \zsh{wrapper}가 원본 함수의 반환값을 그대로 전달한다면 새로운 Tensor를 자동으로 복사하는 것은 아니다.

반환 객체의 동일성, 내부 상태, 계산 그래프와 같은 특성은 실제 \zsh{wrapper}가 어떤 연산을 수행하는지에 따라 결정된다.

\subsubsection{예외(Exception)가 발생하면 호출 흐름은 어떻게 될까?}
